# 当前推理效率与 OpenRouter Batch 审查

2026-10-18，离线检查执行代码及已有运行记录，并只读查询官方文档和端点。没有新增付费推理，没有修改执行逻辑。

## 当前调用方式

当前每个KT目标独立POST到 chat/completions，返回一个概率。asyncio启动8个worker，共享httpx.AsyncClient连接池；这是普通API的异步并发，不是服务商Batch API，也没有把多名学生的目标合入同一条模型提示。

本次实验配置 max_concurrency=8、requests_per_minute=600（发起间隔至少0.1秒）、max_attempts=2、timeout_seconds=60、max_requests=450。max_requests是本次调用的HTTP尝试上限，不是batch size。已有attempt时间区间观察到峰值并发确为8。

每个目标的合法真实历史已预先构造，计算下一目标不依赖上一步模型概率，因此并发不会改变历史更新协议。

R2单请求平均输入约2806 token、输出约13 token。R2测试有一次31.04秒的长尾请求，不能以平均值当作每次完成承诺。记录的单请求latency包含HTTP往返及部分响应处理，不是纯模型生成时间；elapsed是执行阶段，不涵盖全部启动准备、评估和最终完整性校验。

R2验证的请求latency合计约412.99秒，除以8约51.62秒，实际56.57秒；折算平均在途约7.30。说明小规模运行已较充分利用8路并发，但这不是独立CPU/IO剖析，不能据此精确归因额外耗时。

## 放大消融前值得处理的点

1. 同学生请求缺少串行调度。R2验证42个同学生目标转换中41个存在请求时间重叠；11个同起点历史增长机会全部重叠。R2测试44个转换全部重叠，12个同起点增长机会也全部重叠。这不破坏标签协议，但可能使前一条缓存尚未建立，降低复用机会。候选策略是同学生顺序、跨学生并发，维持总并发8；是否实际省钱需测量，不能保证。
2. 主执行器没有设置按学生的会话亲和性header；之前缓存探索工具的串行与x-session-id不能当作生产runtime已经实现。会话亲和性也不保证后端缓存命中。
3. 预算reserve与settle都会同步重写整个JSON账本，totals还遍历历史尝试；单事件循环里这些操作会阻塞其他worker。请求、响应、哈希与SQLite提交也同步进行。对数百目标可以使用，对大量消融应考虑事务化预算与独立写入队列，保留先预留后请求的安全语义。
4. 每次请求结束glob扫描requests/responses目录找自己的文件，目标增大时累计扫描开销增长。已知文件名可直接寻址，不必重复枚举全目录。
5. 当前共享预算只适用于依次启动各run。不能直接用多个进程同时跑不同消融组并写同一JSON预算；必须先增加跨进程事务/锁保护。
6. prepared与输入/目标列表完整载入内存，且请求在初始化求hash与实际执行时重复渲染。当前272目标很小，不能把这套方式直接推断为能高效处理完整原始NIPS的几十万目标。

优先改善缓存调度与持久化方式，而不是直接把并发从8提到几十。当前600 RPM上限高于实际约190–286 RPM，限速不是观察到的主要吞吐约束。增加并发是否划算需另测供应商限流、长尾和错误率。

## 600 RPM 的来源与调节

600 RPM是本项目实验配置自行设定的客户端节流，不是已确认的OpenRouter或Tenstorrent官方额度。2026-10-18官方Limits文档说明，付费模型没有统一的平台请求次数上限，但上游供应商容量和平台保护仍可能返回429；成功响应不提供X-RateLimit-*，平台429才可能提供相关限流头，Retry-After存在时应遵守。当前没有取得Tenstorrent针对此模型和账户的固定额度，不能将600当作官方值。

可考虑以8→16→24逐级测试自适应并发，在无429且成功吞吐提升时增加，遇429/503或长尾恶化时降低并退避。并发数与RPM分开控制；若保留600 RPM，平均请求2秒时约20个在途请求才可能接近每秒10次发起。该数值是容量估算，不是已测结果。应同时保持同学生顺序、跨学生并发及持久化费用预留；本次只审查，未实施调度改动或发起压测。

限流资料：https://openrouter.ai/docs/api-reference/limits

## OpenRouter 是否支持 Batch API

官方已提供异步Batch API：POST /api/v1/batches提交，GET /api/v1/batches/{id}查询；每条用custom_id映射结果。请求通过内联requests数组提交，不是上传JSONL。一个batch固定同一模型及供应商，可提交多个独立KT目标，每个目标仍携带自己的完整合法历史。

官方说明批处理通常有折扣，但实际按具体batch端点价格计费，不能保证所有模型打五折，也不能假定与prompt缓存折扣直接相乘。通常采用24h完成窗口，部分供应商期限更长；不保证比当前一分钟左右的实时并发更快。Batch也不保证按学生时间顺序执行，不能假定前缀会先预热后复用。

本次只读查询：

- qwen/qwen3.8-27b:batch/endpoints 返回 endpoints=[]。
- qwen/qwen3.6-35b-a3b:batch/endpoints 也返回 endpoints=[]。

因此当前公开元数据未列出项目这两款模型的可用batch端点，不能直接把Tenstorrent同步路由改为Batch。项目目前也没有batch提交、轮询与结果归并适配器。若以后支持，应保留custom_id→sample_id、提交身份、费用预留、原始响应缓存、失败恢复及去重，不能只改一个URL。
