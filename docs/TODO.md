### 目标与边界

在保持同一数据划分、目标集合、可见历史、模型及评估口径的前提下，降低总调用费用和延迟。不能只追求缓存命中率，也不能为复用缓存改变 KT 协议。

区分两类缓存：

| 类型 | 作用 | 当前状态 |
|---|---|---|
| 本地结果缓存 | 成功目标续跑时直接读取已有预测，不再调用 API | 已实现，限同一个 run |
| 供应商提示缓存 | 请求仍执行，复用相同输入前缀，可能降低输入费用与延迟 | 取决于模型、端点及供应商，尚未专门适配或验证 |

主动重复实验不能把本地缓存命中当成一次新的独立模型调用。

### 已确认的信息

- OpenRouter 当前 Jev 1.14 端点元数据为 `supports_implicit_caching=false`，未给出缓存读取价格。尚无依据承诺它能通过跨请求前缀缓存获得折扣；该字段不证明内部绝对没有缓存。
- 所读 TypeSafe API 文档没有明确给出跨请求提示缓存的控制与计费契约。不能把 Chat 缓存参数直接套用到 Decisions API。
- Qwen 示例模型 `qwen/qwen3.6-35b-a3b` 的不同供应商端点存在缓存支持和读取价格差异。部分端点虽然支持隐式缓存，但缓存读取价格与普通输入相同，因此命中不一定降低输入费用。
- 当前 Chat 适配器用 `canonical(item.state())` 构造内容；按键排序使 `current_item` 出现在 `history` 前，变化的当前题目会较早打断公共前缀。
- 对相邻目标，增长中的历史前缀有复用潜力；进入固定长度窗口的滚动阶段后，最早记录被移除，历史开头变化，会削弱前缀复用。
- OpenRouter 提供供应商粘性路由及缓存用量信息。后续应检查实际缓存读取、写入及费用，不能只凭输入相似度推测命中。
